# Account cleanup and identity update — 2026-09-28

## Account erasure checks

The specifically requested account was removed from the live Turso database with an exact email-and-ID predicate in a transaction. Foreign-key enforcement was verified before deletion; all 15 user-linked tables and conversation child tables were checked afterwards. Other accounts were preserved. A follow-up check found no matching account or email reference in the verification table.

A separate disposable production account was populated with profile, services, languages, taste, feedback, history, watchlist, events, conversations/messages/displayed titles, context, AI usage, channel favorite and reminder records. Deleting through the actual `/api/auth/delete-user` endpoint removed its data; all 15 user-linked tables and the indirect conversation tables were empty for that identity. Its old session was rejected. Re-registering the same test email produced a different identity, incomplete onboarding and empty taste/history/watchlist/feedback. The recreated test account was also deleted.

This verifies active application/database erasure, not literal erasure of every infrastructure trace. Provider logs, disaster-recovery backups, or notifications already stored on another/offline device are not claimed to be remotely purged. Public TMDB artwork/cache and shared EPG records are intentionally not removed with an account. No personal data or credentials are included in this report.

## Deletion UX correction

The audit found Better Auth rejects password-free deletion from a session older than its freshness threshold with `SESSION_EXPIRED`. The app now asks for the current password in a confirmation sheet with show/hide control, prevents repeated submission, and reports failures without pretending deletion succeeded. Local in-memory data is reset even if notification cancellation fails after successful remote deletion; that failure is explicitly reported. Secure bearer storage is cleared after successful deletion. The notification-plugin cancellation path is covered by a mobile test.

Backend regression checks cover incorrect-password refusal, successful password-confirmed deletion from an older session, session invalidation, and the authenticated profile name. Production data-cascade verification used a fresh session; the older-session password path was validated locally against the real Better Auth handler and migrated SQLite schema.

## UI and branding

- Password reveal/conceal on both login and registration; independent invite-code reveal/conceal on registration. Switching modes conceals the fields again. No actual secrets appear in screenshots.
- Profile displays the authenticated user's stored name instead of a hard-coded Nex viewer label; no additional profile request is needed.
- Login/registration use a compact logo, short heading and form, without the long marketing subtitle or demo disclaimer paragraph.
- Approved Nex N launcher artwork and native in-app vector mark, without a background behind the in-app mark. Light mode uses a darker face color for contrast. Android/iOS/web names are Nex.
- The source asset and generation prompt are documented in `mobile/assets/branding/README.md`. Platform icons are generated by a development-only tool; no new runtime service or paid dependency was introduced.
